# @librephotos/local-db

The on-device SQLite database of the LibrePhotos apps. The mobile app (Expo)
uses it today and the desktop app (Tauri 2) is moving onto it, so both store,
query and change local data the same way. It owns:

- the Drizzle schema (`src/schema.ts`) and its row types,
- the migrations (`migrations/`, plus `migrations.json` for other runtimes),
- every query (`src/queries/`) and writer (`src/writers.ts`),
- the change hub (`src/change-hub.ts`): table-level change fan-out with the
  coalescing that keeps a camera-roll scan from re-running every query per row,
- reset and wipe logic (`src/reset.ts`, `src/migrate.ts`),
- the in-memory test database (`@librephotos/local-db/testing`).

Platform code stays in the apps. An app provides one thing: an **executor**.

TS source, consumed directly (Metro, jest, vitest and Vite compile it), like
`packages/api-client`. Everything is async.

The developer docs page [On-device database](https://docs.librephotos.com/docs/development/local-database)
(`apps/docs/docs/development/local-database.md`) explains the design: the executor
contract, batches instead of transactions, migrations, the change hub, live queries,
and how to add a query or a column.

## The executor

```ts
import type { SqlExecutor } from "@librephotos/local-db";

interface SqlExecutor {
  exec(sql: string, params: SqlValue[], method: "run" | "all" | "get" | "values"): Promise<SqlResult>;
  batch(statements: { sql: string; params: SqlValue[]; method: SqlMethod }[]): Promise<SqlResult[]>;
}
type SqlValue = string | number | bigint | Uint8Array | null;
type SqlRow = SqlValue[];
type Meta = { columns?: string[]; changes?: number; lastInsertRowId?: number };
type SqlResult = (Meta & { rows: SqlRow[] }) /* run, all, values */ | (Meta & { rows: SqlRow | undefined }) /* get */;
```

- `exec` runs one statement with positional `?` parameters (booleans arrive as
  0/1). Rows are Drizzle sqlite-proxy's shapes: **positional arrays**, `"all"` /
  `"values"` a list of rows, `"get"` the first row or `undefined`, `"run"` `[]`
  (report `changes` / `lastInsertRowId` when you know them). A statement with
  `RETURNING` arrives as `"all"` or `"get"` and is stepped to the end, so it
  writes every row.
- `columns` (the statement's column names, in order) is **required for `"all"`
  and `"get"`**: every query here is raw SQL whose rows are read by name, and
  only the engine knows the names (rusqlite: `Statement::column_names()`).
- `batch` runs its statements in order in **one transaction**, all or nothing,
  and returns one result per statement. Nothing else may run on the connection
  in between (serialize your calls; on the desktop a `Mutex<Connection>` does it).

There is no "open a transaction and give it back": an async executor shared by
concurrent callers cannot hold one open while others keep issuing statements.
Atomic writes are a batch (`runBatch(db, statements)` / `db.batch([...])`), and a
read-then-write that must be atomic is one statement
(`UPDATE ... WHERE id = (SELECT ...) RETURNING ...`, see `claimNextUpload`).
`db.transaction()` rejects, and the package's lint bans calling it.

Implementations:

| Runtime | Executor | Where |
| --- | --- | --- |
| Node (tests, tools) | `createBetterSqliteExecutor(db)` | `@librephotos/local-db/better-sqlite3` |
| Phone | `createExpoExecutor(sqlite)` (expo-sqlite async API, serial queue, WAL, statement LRU) | `apps/mobile/src/db/client.ts` |
| Desktop | `executor` over the Tauri commands `db_exec` / `db_batch` (rusqlite; JSON answers written while SQLite steps) | `apps/desktop/src/db/executor.ts` |

Then:

```ts
import { createDatabase, runMigrations } from "@librephotos/local-db";

await runMigrations(executor);         // before any query
const db = createDatabase(executor);   // AppDatabase: Drizzle's sqlite-proxy database
const page = await timelinePage(db, { limit: 120 });
```

`AppDatabase` is Drizzle's async SQLite database (`drizzle-orm/sqlite-proxy`).
Raw SQL (`db.all<Row>(sql\`...\`)`, which every query here uses) returns rows as
objects; Drizzle's query builder works as usual on the same database.

## Migrations

`migrations/*.sql` + `meta/_journal.json` are generated by drizzle-kit from
`src/schema.ts`; `0001_local_search.sql` is hand-written (FTS5). Change the
schema, then run `npm run db:generate --workspace packages/local-db`
(`drizzle-kit generate` + `scripts/build-migrations.mjs`). That writes
`migrations/migrations.json`:

```json
[
  { "tag": "0000_baseline", "statements": ["CREATE TABLE `app_meta` (...)", "..."] },
  { "tag": "0001_local_search", "statements": ["CREATE VIRTUAL TABLE ...", "CREATE TRIGGER ... END;"] }
]
```

Every runtime applies that file and nothing else. Each statement is one
executable statement (trigger bodies included). Bookkeeping, shared by all
runtimes:

```sql
CREATE TABLE IF NOT EXISTS __local_db_migrations (tag TEXT PRIMARY KEY, applied_at INTEGER NOT NULL);
```

The algorithm (`runMigrations`), to implement the same way in Rust:

1. Create the bookkeeping table if missing, read the applied tags.
2. For each migration in array order whose tag is not applied: in ONE
   transaction, run its statements, then
   `INSERT INTO __local_db_migrations (tag, applied_at) VALUES (?, <ms epoch>)`.
3. If anything fails: **wipe and rebuild**. Read every row of `outbox` and
   `upload_queue`, drop every view, then every table except FTS shadow tables
   (they go with their virtual table), recreate the bookkeeping table, apply all
   migrations (recording each), and re-insert the saved rows with only the
   columns that still exist (`INSERT OR IGNORE`). The remote mirror is
   disposable; the app re-seeds it.

From Rust: `const MIGRATIONS: &str = include_str!("<path>/packages/local-db/migrations/migrations.json");`,
parse with serde into `Vec<{ tag: String, statements: Vec<String> }>`, and
`execute_batch` each statement inside a transaction.

CI (`.github/workflows/local-db.yml`) runs `node scripts/build-migrations.mjs --check`
and a test that `migrations.json` matches the SQL files. The mobile app has
never shipped, so the history was squashed into one baseline; from now on
migrations only append.

## Change hub

`createChangeHub({ subscribe, defer? })` turns raw change events (one per row
from SQLite's update hook) into a few flushes per second, scoped by table:
`hub.watch(tables | null, (changed) => ...)`. A runtime feeds it either its
update hook (the phone: expo-sqlite's `addDatabaseChangeListener`; the desktop:
rusqlite's `update_hook` forwarded as Tauri events) or `trackChanges(executor)`,
which wraps any executor and reports each written table once per statement.
Writes made by triggers (the FTS index) are not reported; watch `local_asset`.

The apps put their live queries on it (mobile: `apps/mobile/src/db/provider.tsx`,
a TanStack Query observer per key, invalidated by hub flushes).

## Local search (FTS5)

`local_asset_fts` indexes every local asset under its name (extension
included), kind ("raw photo", "video movie", "photo picture image"), `folder`
words, date words from `bucket_day` (year, month name long and short,
`yyyy-mm`, `yyyy-mm-dd`), "undated" when the metadata pass found no date, and
format, camera and lens. The terms are defined once, in the view
`local_asset_search_terms`; triggers on `local_asset` (insert, update of those
columns, delete) keep the index in sync, so any runtime that applies the
migrations gets it. The FTS rowid is `local_asset.rowid`: after a `VACUUM` run
`rebuildLocalSearch(db)`. Query with `searchLocalAssets(db, "march 2023 canon")`
(every word must prefix-match; `ftsQuery` builds the MATCH expression).
better-sqlite3 and expo-sqlite (unless `enableFTS: false`) both ship FTS5.

## The desktop folder library

The desktop's "folders the user added" map onto the same tables as the phone's
camera roll:

| Desktop | Table |
| --- | --- |
| a folder root | `local_album` with `source = 'folder'`, `path`, `added_at`, `backup_selection` |
| a file | `local_asset` (`uri` = absolute path; `folder`, `size_bytes`, `taken_at`, `camera`, `lens`, `latitude`, `longitude`, `format`, `meta_state`, `bucket_day`) linked to its root by `local_album_asset` |
| MD5 / server hash | `local_asset.hash` |
| backup state | `upload_queue` (`upload_id`, `upload_offset` for resumable uploads) |

Queries (`src/queries/library.ts`, `upload-queue.ts`, `local-search.ts`):
`folderRoots`, `addFolderRoot`, `removeFolderRoot`, `mergeFolderRoot`,
`setFolderBackup`, `knownFolderFiles`, and for the file seams `upsertWalkedFiles`
(walk batches, watcher created/modified), `removeLocalPaths` (a path and
everything below it), `renameLocalPaths` (files and folder prefixes; the row,
its hash and upload state survive), `pendingMetadata` + `applyFileMetadata`
(`FileMeta` batches; dated files sort by `takenMs`), `pendingHashes` +
`setFileHashes` (MD5 + user id, the server's image hash),
`localTimelineDays`, `localTimelinePage`, `localAssetsByHash`, `localAssetByUri`,
`searchLocalAssets`, `rebuildLocalSearch`, `enqueueBackups`, `requestUpload`,
`claimExistenceChecks`, `claimNextUpload`, `setUploadProgress`, `markDone`,
`markSkipped`, `markAbsent` (a checked file goes to the uploaders and is not
checked again), `markFailed`, `resetInFlightUploads`, `localBackupCounts`, and
`upsertLooseFile` (a file outside the roots the user asked about),
`markHashUnreadable`, `libraryProgress`, `cancelFolderBackups` (backup turned
off), `recordServerHas` (a single "the server has it" answer) and
`switchFolderAccount` (hashes rebuilt for another server account).
