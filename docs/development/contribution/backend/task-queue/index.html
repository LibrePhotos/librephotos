Task queue and parallel workers

Not released yet (comes after 1.6.0) Status: phases 0 to 4 are in: the queue runs every job, manage.py run_workers replaced qcluster, django-q2 is gone (its tables stay one release for the upgrade), Scan Faces fans out, and the width follows PARALLEL_WORKERS and the capacity check at runtime (api/jobs/parallel.py, GET/PATCH /api/parallel-workers/ for admins), shown in the first-time setup and the site settings. What is left is in the last paragraph below.

This page is the plan for #3073: a queue that LibrePhotos owns, so that the number of parallel workers can follow what the machine (or the container) really has, and so that parallel lanes do their work once.

Why not keep django-q2​

Every enqueue already goes through one seam, apps/backend/api/jobs/queue.py. Behind it, LibrePhotos works around django-q2 in many places:

NeedTodayWhere
A task of a dead cluster runs againa broker subclass with a renewed 10-minute lease (#2852, #2876)api/jobs/broker.py
An old container must not run the new release's tasksthe same subclass checks for unknown migrations before each dequeue (#2848)api/jobs/broker.py
A task whose function moved fails once, not forevera tolerant unpickler and a hand-written failure record (#2945)api/jobs/broker.py
Stuck-job cleanup knows which jobs are aliveunpickles every queued payload (held_job_ids, #2879)api/jobs/queue.py
Cancel drops the queued tasks of a jobunpickles every queued payload (remove_queued_tasks)api/jobs/queue.py
Nominatim gets at most one request per seconda file-locked SQLite database per host (django-q2#350 stalled)api/geocode/rate_limit.py
How many workerscpu_count() of the host, ignoring a container limit; 2 in the standalone buildsettings/production.py, settings/standalone.py
Memorymax_rss and recycle, checked only between tasksQ_CLUSTER

Payloads are pickles: 37 enqueue sites pickle a whole User, a moved function breaks the queue, and nothing can be read from a queued task without unpickling it. A chain continues after a cancelled or failed step, which is how a cancelled Generate Face Embeddings started four Find Similar Faces at once (#3073).

The queue below is about 1,000 lines with tests, replaces broker.py and rate_limit.py, and keeps the seam's functions, so the ~49 call sites do not change.

Tables​

All in the api app, written only by api/jobs/ (the models hold data and queries, as everywhere).

A task that succeeds is deleted in the transaction that ends it; failed and cancelled rows are kept for 7 days (the daily old-job cleanup deletes them). Indexes: (status, queue, priority desc, id) partial on status='queued', (job_id), (status, lease_until) partial on status='running'.

api_taskgroup: id, total, ended (counter), fired (bool). api_taskschedule: name (unique, null), func, args, kwargs, schedule_type (O once, I minutes, H hourly, D daily: the letters django-q2 used), minutes, next_run, intended_date_kwarg, last_run. api_workerprocess: one row per live worker (name, host, pid, slot, started_at, heartbeat_at, rss_mb, task_id, recycled_for): the admin's Workers panel reads it. api_throttle: key (pk), next_at.

Payloads​

api/jobs/payload.py encodes None, bool, int, float, str, lists, tuples, dicts with string keys, UUID, datetime, date, and a model instance as {"__model__": "api.user", "pk": 1}. The worker loads the instance again when the task runs, so a task works on the row as it is then, not on a copy from when it was queued, and call sites keep passing user. Anything else is a TypeError at enqueue time, in the request that queued it, not in the worker.

Claiming​

A worker claims one task per transaction. On PostgreSQL:

UPDATE api_queuedtask
   SET status = 'running', worker = %(worker)s, attempts = attempts + 1,
       started_at = now(), lease_until = now() + interval '10 minutes'
 WHERE id = (SELECT id FROM api_queuedtask
              WHERE status = 'queued' AND run_after <= now() AND queue = ANY(%(queues)s)
              ORDER BY priority DESC, id
              LIMIT 1
              FOR UPDATE SKIP LOCKED)
RETURNING id, func, args, kwargs, job_id, attempts;

SKIP LOCKED lets N workers claim in parallel without waiting for each other. SQLite has no row locks: there the same SELECT ... LIMIT 1 and UPDATE ... WHERE id = ? AND status = 'queued' run in one BEGIN IMMEDIATE transaction (transaction_mode=IMMEDIATE, settings/_sqlite.py), which takes the database's write lock first, so claims are serialised and never double. Both go through the ORM (select_for_update(skip_locked=True), which Django leaves out on SQLite).

The queues a worker asks for depend on the caps: heavy only while fewer than heavy_width heavy tasks run, geocode while none runs. The count and the claim share the transaction; on PostgreSQL a pg_advisory_xact_lock per capped queue makes the count exact across hosts.

Leases. Each worker renews lease_until of its task every minute from a thread. The supervisor requeues the task of a worker it saw die at once; any supervisor requeues a running row whose lease ran out (a host that went away) within a minute. A requeued task with attempts >= max_attempts becomes failed, so a photo that kills its worker every time stops after three tries instead of looping. The supervisor's warning about a worker that died (killed for memory by the system, say) names the task it was running, and is a warning, not an error report.

Database errors. A worker that cannot claim a task, or record the end of one, because the database fails (locked past the timeout, a dropped connection, a damaged SQLite file) logs a warning and tries again, waiting twice as long each time up to a minute, instead of exiting. A task whose end it could not record runs again once its lease runs out. Up to 1.6.0 django-q2's pusher and monitor exited on such an error and were started again ("reincarnated pusher ... after sudden death").

Release guard. Before each claim a worker checks, with one count(*) of django_migrations, whether anything was applied since its last look, and only then compares names (unknown_applied_migrations). When the database has a migration this code lacks, the worker stops claiming and the old container's tasks finish under their leases (#2848).

A task whose function is gone fails at claim time with "<path> no longer exists, an older release queued it", without retries (#2945).

Processes​

manage.py run_workers  (supervisor: one per host or container)
├── scheduler thread     due schedules → tasks, catch_up=False
├── reaper thread        expired leases → queued / failed; leases of dead workers at once
├── capacity thread      every 30 s: capacity check → width W (shared multiprocessing.Value)
└── worker 0 .. N_max-1  spawned processes; worker i claims only while i < W
      └── lease thread, memory watchdog thread
  • The supervisor replaces qcluster, its sentinel, pusher and monitor. Workers are started with multiprocessing spawn on every platform, so Linux and Windows behave alike, and in the standalone build from the librephotos-worker link as today.
  • N_max processes start; W (the effective width) changes at runtime without a restart, from the setting, the capacity check and the memory left. Workers above W idle on a 1 s poll and cost their idle RSS (~110 MB), which the budget counts.
  • Stop. POSIX: SIGTERM/SIGINT. Windows has no SIGTERM, so the standalone launcher starts the supervisor with --stop-on-stdin-eof and a pipe on stdin; closing it (or the launcher dying) is the stop. The supervisor sets a shared stop event, workers finish their task, and after 25 s the rest are killed and their tasks requeued. Processes are always stopped by PID tree, never by a command-line filter.
  • Graceful in the task. api.jobs.worker_runtime.checkpoint() raises WorkerStopping (a BaseException, so a task's except Exception does not swallow it) when the worker must stop or recycle. A task that calls it between items (the Scan Faces chunk, Generate Face Embeddings) is requeued without an attempt and resumes: its items are counted once (CountedJobItem), and the chunk skips photos already counted.

Chains, groups, deduplication, cancel​

  • Chain. enqueue_chain writes every step at once: the first queued, each next one waiting with after on the previous. When a step ends, its successor becomes queued if the step succeeded (the task returned and its job row is neither cancelled nor failed), else it is cancelled together with its job row ("an earlier step did not finish") and the rest of the chain, unless the successor has continue_on_error. The scan's follow-ups and the model download before a scan keep today's behaviour with continue_on_error=True; new chains stop by default.
  • Group barrier. enqueue_group(tasks, then=step) writes a taskgroup with total = len(tasks), the members, and the follow-up as waiting. Whenever a member ends (succeeded, failed after its last attempt, or cancelled), the same transaction runs UPDATE api_taskgroup SET ended = ended + 1 and reads it back; the transaction that brings ended to total sets fired and queues the follow-up. Failed and cancelled members count as ended, so the follow-up always runs exactly once; it decides itself what to do about a cancelled job.
  • Dedupe. A partial unique index on dedupe_key where status in ('waiting','queued','running'). enqueue_followup(..., dedupe_key=...) inserts the job row and the task in a savepoint; on the IntegrityError it rolls both back and returns the existing job. Generate Face Embeddings and Find Similar Faces queued by Scan Faces use faces:embeddings:<user> and faces:cluster:<user>.
  • Cancel is UPDATE api_queuedtask SET status='cancelled' WHERE job_id = %s AND status IN ('waiting','queued'), plus the chain rule above for their successors and the group rule for their barrier. No payload is opened. A running task still checks its job row (stop_if_cancelled).
  • Enqueue is transactional. The task row is written in the transaction that writes the job row, so transaction.on_commit and the "could not queue the job" failure path go away: either both exist or neither.
  • held_job_ids for the stuck-job cleanup is SELECT DISTINCT job_id ... WHERE status IN ('waiting','queued','running').
  • One job row, many writers. Every task of a fan-out job reports into the job's result JSON (update_job_result in api/directory_watcher/utils.py: errors, counts, the face service's unreachable streak; LongRunningJob._merge_result when it ends). Each write reads the row select_for_update in a transaction and writes it back there, so concurrent writers queue on the row lock (on SQLite, on the write lock BEGIN IMMEDIATE takes) and none is lost or refused. Not released yet (comes after 1.6.0) Up to 1.6.0 this was a compare-and-swap that read the row, wrote only if result was still what it read, and gave up after 50 tries. When many workers wrote at once (say a Scan Faces whose face service was down, every chunk writing an error per photo), a worker could lose 50 races in a row ("gave up updating its result after 50 conflicting writes"), and the item it was counting was never counted, so the job could not reach its target.

Scheduler​

api_taskschedule replaces django_q_schedule with the four types in use. The scheduler thread looks every 5 s for next_run <= now, and fires a schedule with a conditional update (SET next_run = <next> WHERE id = %s AND next_run = <the value it read>), so two supervisors never fire it twice. catch_up is off: the next run is the first one after now, so a minutely schedule missed for an hour runs once (today's "catch_up": False, #2848). ONCE rows are deleted when they fire. With intended_date_kwarg the task gets the run's due time in ISO format, as django-q2 passed it. The start_* management commands still create the schedules at boot, through the same ensure_schedule/replace_schedule.

Throttle​

Not released yet (comes after 1.6.0) Up to 1.6.0 the geocoding rate limit was a file-locked SQLite database under BASE_DATA (geocode_rate_limit.sqlite3), which only held on one host. That file is no longer used.

api/jobs/throttle.py wait(key, seconds): UPDATE api_throttle SET next_at = now + seconds WHERE key = %s AND next_at <= now; one row updated means go, otherwise sleep until next_at and try again. It is in the main database, so it holds across processes and across hosts (the file lock it replaces only held on one host). Reverse geocoding calls it per provider (Nominatim 1.1 s), and geolocation tasks run in the geocode queue, capped at one at a time, so the other workers do other work instead of sleeping.

Memory​

  • Hard limit per worker. The watchdog thread reads the worker's RSS every 2 s; above hard_limit it requeues the task (an attempt counts) and exits at once. The supervisor starts a new worker and records recycled_for (shown in the admin).
  • Soft limit per worker. Above soft_limit (0.75 × hard_limit) the next checkpoint() raises WorkerStopping: the task is requeued without an attempt and the worker exits to be replaced. A task without checkpoints finishes first. This covers the inside of long tasks, which max_rss never did.
  • Machine. When the capacity check sees less than low_water available memory (the larger of 512 MB and 10 % of the limit), it lowers W by one per round, down to 1; it raises it back by one per round once there is room again.
  • hard_limit defaults to max(600 MB, lane_ram) and can be set (WORKER_MEMORY_LIMIT_MB).

Capacity and the worker count​

api/runtime/capacity.py has no Django imports, so sidecars can use it.

QuantityLinux, Docker, KubernetesWindows
RAM totalmin(host, cgroup): v2 memory.max, v1 memory.limit_in_bytesmin(host, Job Object limit) (QueryInformationJobObject)
RAM availablemin(host available, limit - (usage - inactive_file))host available
Coresos.process_cpu_count() (affinity, --cpuset-cpus), capped by cpu.max or cfs_quota_us / cfs_period_usos.process_cpu_count()
GPU, VRAMnvidia-smi through api.runtime.binaries; unknown otherwisesame

fixed   = web 300 MB + the enabled sidecars (SIDECAR_MB) + one face service (FACE_COSTS)
          (available counts what LibrePhotos' own workers and sidecars hold, so it does not shrink as they run)
N_cpu   = Gentle 1 · Balanced clamp(cores // 2, 1, 4) · Fast clamp(cores - 1, 1, 8)
N_ram   = floor((budget - fixed) / lane_ram)            lane_ram: 600 MB light, 750 MB heavy (CPU)
N_vram  = floor((vram_free - 512 MB) / vram_per_lane)   only with a GPU provider
W       = max(1, min(N_cpu, N_ram, N_vram, WORKER_CONCURRENCY if set))
heavy_width = max(1, min(W, N_ram_heavy, N_vram))

On SQLite W is capped at 4: one writer, more lanes only wait for it. N never drops below 1; when even one lane does not fit the admin sees a warning and LibrePhotos runs slowly instead of not at all.

The setting. PARALLEL_WORKERS (site setting): gentle, balanced (default), fast. Fast first import switches itself back to Balanced once the queue has been empty for 10 minutes after a completed library scan. WORKER_CONCURRENCY stays a hard override (also of N_max). N_max is W of Fast at start, so switching up needs no restart unless the machine got bigger.

Where it shows. The first-time setup gets a step after the library path: what was detected ("4 cores, 8 GB (container limit), no GPU"), the three intentions with the resulting workers and memory budget each, and a warning when the choice does not fit ("4 workers need about 3 GB, this container has 2 GB; 2 will run"). The same control is in Settings (admin) and the admin's server stats show the running width, the budget in use and the recycles.

Scan Faces in parallel​

scan_faces lists the photos once (as today), then queues scan_faces_chunk(job_id, photo_ids) tasks of 64 photos in the heavy queue, as one group whose follow-up is finish_face_scan(job_id). Each chunk counts its photos with an item key, so a redelivered chunk counts nothing twice. With one worker the chunks run in listing order, which is today's order. The follow-up runs once, after the last chunk, whatever happened to the others: when the job was cancelled it does nothing; otherwise it completes the job and queues Generate Face Embeddings, then Find Similar Faces, as a stopping chain with the dedupe keys above. The 20-in-a-row "face service unreachable" counter moves into the job's result, so it spans chunks.

This does not touch the clustering itself. @metamountain's fixes on faces-large-libraries (batched pk__in for SQLite's 32,766-variable limit, counting a person once per photo) are independent of it.

Face services, one per heavy lane​

Not released yet (comes after 1.6.0) The face sidecar serves one request at a time, so N heavy lanes on one face sidecar mostly queue. api/runtime/replicas.py (no Django) and api/runtime/sidecar_scaler.py give it replicas; the mechanism is generic (REPLICA_KINDS), only face_recognition opts in.

  • Ports. Replica i listens on SIDECAR_PORT_FACE_RECOGNITION + 100 × i (i up to 7). The process is main.py --replica i (service face_recognition --replica i in the standalone build), /health answers its replica and, once a model is loaded, its device (cpu, webgpu, cuda). A port that answers as another program, or as another replica, is FOREIGN for that replica alone. Replica 0 is the sidecar as before: start_service starts it and the minute watchdog keeps it.
  • Owner. The run_workers supervisor of each host runs the scaler every 5 s in a thread of its own (one run at a time). It starts replicas 1.. while the heavy queue has queued or running tasks, at most min(plan, heavy width, open heavy tasks), waits until each answers as itself, and writes the live ports and the device to <tempdir>/librephotos-sidecars/<service>-<port>.json. A replica no longer wanted leaves that list at once and stops when it is idle (no request for 120 s, or 120 s after it was dropped; at once when the plan no longer allows it or memory is low, but never while busy). Exiting rather than unloading frees WebGPU memory and glibc's heap. On shutdown (signal or stop file) the supervisor stops them after the workers; a replica left from a killed supervisor is adopted by the next one. Start, stop and restart of a replica happen under a SidecarWatchLease keyed by host, service and replica.
  • Routing. api.runtime.sidecars.post/get read the live list (cached for 1 s, ignored when older than 2 minutes, so a dead supervisor falls back to replica 0). A worker starts at replica slot % live (set_lane in worker_entry), the web process at pid % live; it takes a non-blocking file lock per port (port-<port>.lock, msvcrt.locking / flock) and moves on to the next free replica, so a request never waits behind another lane's while one is free. With none free it goes to its own replica and queues there. A refused connection fails over to the next replica at once (no connect retries) and skips that one for 10 s; an error answer or a read timeout is raised as before. The drawn-box calls in views/faces.py go through the same client.
  • Plan. plan_workers(..., load=Load(...)) replaces FIXED_MB. After the workers and heavy lanes:
spare     = room - W × 600 MB - heavy × 150 MB
replicas  = clamp(min(heavy,
                      1 + spare // face_mb,
                      vram_budget // face_vram_mb   (GPU, VRAM known),
                      2                             (GPU, VRAM known: one GPU's queue),
                      1                             (GPU, VRAM unknown),
                      FACE_SIDECAR_REPLICAS if set), 1, 8)
vram_budget = 0.8 × (nvidia-smi free + what our face services hold)

FACE_COSTS is a table per model and device (CPU vs GPU), measured (peak memory plus headroom) on Windows and Linux (glibc) for the CPU and WebGPU on Windows. The device comes from the replicas' /health; before any model is loaded it is unknown (GPU costs, one replica) unless ONNX_PROVIDERS starts with the CPU or the WebGPU plugin is missing. FACE_SIDECAR_REPLICAS only lowers the result; a higher value is logged and capped.

  • At runtime. When memory is low (low_on_memory), the scaler takes one replica away per round, down to 1, before the sizer has to pause workers. A replica above max(2 × cost, cost + 500 MB) is restarted; replica 0 only when idle. On the CPU, replicas 1.. start with ONNX_INTRA_OP_THREADS = min(cores, physical cores) // replicas unless the variable is set; replica 0 keeps ONNX Runtime's default.
  • Shown in GET /api/parallel-workers/: per plan face_replicas, face_replica_mb, face_vram_mb, face_device, face_limited_by, vram_budget_mb; face_services (running, live, device, RSS, GPU memory) and face_override.

Upgrade from django-q2​

  • Schedules (no pickles: func is a dotted path, args a Python literal) are copied into api_taskschedule by a migration that reads django_q_schedule with raw SQL when the table exists, keeps next_run, maps the functions moved in 1.5.0 (#2335, what 0157 and 0158 did), and deletes what it copied. It runs before the start_* commands, which then find their schedules and create nothing twice.
  • Queued tasks are signed pickles, so they are read at runtime, not in a migration: on start and every minute while django_q_ormq has rows, the supervisor takes the rows whose lock has expired (a task an old cluster still holds during a rolling deploy is left to it until its lease ends), checks each signature with SECRET_KEY and the cluster name, unpickles it with the tolerant unpickler from broker.py, encodes function, arguments and the remaining chain as a new task, and deletes the old row in the same transaction. A payload that cannot be read is dropped with a warning, and its job, if it has one that has not started, is failed with "queued before the upgrade; start it again". So nothing runs twice, and nothing is lost silently.
  • django-q2 leaves INSTALLED_APPS and the requirements; its tables stay one release so the step above can read them, and a migration in the release after drops them (DROP TABLE IF EXISTS).

Tests​

  • Unit: payload codec round trip and refusal; claim order and caps; lease renewal and expiry; attempts; chain stop and continue_on_error; group barrier with failed and cancelled members; dedupe while queued and running; cancel without payloads; scheduler types, catch_up=False, two schedulers; release guard; throttle; capacity against fake cgroup v1/v2 trees, a Job Object stub and a fake nvidia-smi; the formula as a table.
  • Multi-process, on SQLite and PostgreSQL: N processes claim 2,000 tasks, every task runs once; a worker killed mid-task, lease expiry, exactly one rerun; a supervisor restart while tasks run.
  • Upgrade: a database with pickled django_q_ormq tasks (with User arguments, a chain, a moved function, a bad signature) and django_q_schedule rows is converted, nothing runs twice.
  • Throughput and memory: a real scan of a demo library (and Scan Faces on a copy of a 100k-photo SQLite database) on django-q2 and on the new queue, one and four workers: photos per hour and peak RSS.
  • CI runs the suite on SQLite; a job with a postgres service container runs the queue tests on PostgreSQL.
